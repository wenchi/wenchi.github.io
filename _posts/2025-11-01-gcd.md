在我的 App 開發經驗，通常會來研究並行處理（Concurrency），都是遇到以下這種情境：

1. 有多個任務，需要有序執行，例如：
    - 第一支 API 送出，等待結果以後。此時再打第二支 API，才會有預期行為。
    - 第二支 API 送出時的資料，需要從第一支 API 的結果取得。
2. 有多個任務，需要同時執行，又需要多個任務都有回應後，回傳一個結果，例如：
    - 需要同時從多個資料來源取得資料，可能是同時打多支 API。
3. 數據競爭（Data Race），多個執行緒同時存取同一個記憶體位址，且至少有一個在寫入。

這些情境都非常常見，當然不用官方的 API 也是可以做到，但需要自己寫許多繁瑣的程式，維護性也沒有大家統一使用官方用法來得好。

Apple 目前提供兩套官方方案：

- **GCD（Grand Central Dispatch）**：很早就存在的 C 語言層級 API，用「queue」來管理任務。大量既有專案、Objective-C 程式碼與第三方套件都在使用。
- **Swift Concurrency**：Swift 5.5（2021 年）加入語言本身，包含 `async/await`、`async let`、`TaskGroup`、`actor`、`@MainActor` 等。Swift 6 更進一步，能在編譯時期檢查出 data race。

新的程式碼建議以 Swift Concurrency 為主，但要維護、遷移舊程式，還是得看得懂 GCD。這篇會先介紹兩者的基礎，再用上面三個情境，並排比較兩種寫法。

## GCD 基礎：Dispatch Queue

官方對 Dispatch Queue 的說明如下：

> An object that manages the execution of tasks serially or concurrently on your app’s main thread or on a background thread.

也就是說，我們把任務（block / closure）丟進 queue，由 queue 決定要「一個接一個」還是「同時」執行，以及在哪個 thread 上執行。

### Serial Dispatch Queue

每個任務都需要等待上一個任務完成，才執行下一個任務。`DispatchQueue(label:)` 不指定 `attributes` 時，預設就是 serial queue。

有兩點要注意：

- 「可以同時執行」不代表「保證同時開始」。實際同時跑幾個任務，由系統依照可用的 thread 數量決定。
- 完成的順序不固定。像 `blk1` 與 `blk4` 都睡 1 秒，每次執行誰先印出 `end` 都可能不同，程式不能依賴這個順序。

## Swift Concurrency 基礎：async/await

GCD 的思考方式是「把任務丟到哪個 queue」；Swift Concurrency 的思考方式則是「這個函式是非同步的，呼叫它的地方要等待結果」。

在函式宣告加上 `async`，代表它可能會暫停；呼叫時加上 `await`，代表這裡可能會暫停，等結果回來再繼續：

```swift
func fetchUser() async throws -> User {
    let (data, _) = try await URLSession.shared.data(from: userURL)
    return try JSONDecoder().decode(User.self, from: data)
}
```

幾個重要觀念：

- **`await` 是暫停，不是阻塞。** 等待網路回應的期間，目前的 thread 會被釋放去做其他工作，不像 `Thread.sleep` 或 `semaphore.wait()` 會卡住整條 thread。
- **`await` 前後可能在不同 thread 上。** Swift Concurrency 由系統管理一組 thread pool，我們不再直接指定 thread，而是用 `actor` / `@MainActor` 描述「誰可以存取這份資料」。
- **從同步程式碼進入非同步世界，用 `Task`。** 例如在 UIKit 的按鈕事件裡：

```swift
@IBAction func refreshTapped(_ sender: UIButton) {
    Task {
        let user = try await fetchUser()
        nameLabel.text = user.name
    }
}
```

## 情境 1：有序執行多個非同步任務

### 陷阱：Serial Queue 不能保證非同步 API 依序完成

看完 serial queue 的範例，很容易以為「把兩支 API 依序丟進 serial queue，就會等第一支回來才打第二支」，**但這是錯的**。

上面範例的任務是用 `Thread.sleep` 模擬的**同步**工作，任務結束時工作也真的做完了。可是 `URLSession.dataTask` 這類 API 是**非同步**的：block 只負責「送出 request」，送出後 block 就結束了，serial queue 會立刻開始執行下一個 block。

```swift
let queue = DispatchQueue(label: "com.example.api")

queue.async {
    URLSession.shared.dataTask(with: urlA) { _, _, _ in
        print("A 回來")
    }.resume()
    print("A 送出")
}

queue.async {
    URLSession.shared.dataTask(with: urlB) { _, _, _ in
        print("B 回來")
    }.resume()
    print("B 送出")
}
```

可能的 Log：

```
A 送出
B 送出
B 回來
A 回來
```

Serial queue 保證的是 **block 依序執行**，而不是 **block 裡啟動的非同步工作依序完成**。

### GCD 寫法：巢狀 Completion Handler

用 GCD 時代的寫法，要在第一支 API 的 completion handler 裡再打第二支：

```swift
fetchUser { user in
    fetchOrders(userID: user.id) { orders in
        DispatchQueue.main.async {
            // 回到 main thread 更新 UI
            self.show(orders)
        }
    }
}
```

步驟一多，就會變成層層巢狀的 callback hell，錯誤處理也要在每一層各寫一次。

### Swift Concurrency 寫法：await

```swift
let user = try await fetchUser()
let orders = try await fetchOrders(userID: user.id)
show(orders)
```

程式碼讀起來就像同步程式一樣由上而下，第二行一定會等第一行完成才執行，任何一步拋出錯誤，都可以用同一個 `do/catch` 處理。

## 情境 2：同時執行，全部完成後再處理

### GCD 寫法：DispatchGroup

`DispatchGroup` 可以追蹤一組任務，等全部完成後再通知。打非同步 API 時，要搭配 `enter()` / `leave()` 使用：

```swift
let group = DispatchGroup()
var profile: Profile?
var orders: [Order] = []

group.enter()
fetchProfile { result in
    profile = result
    group.leave()
}

group.enter()
fetchOrders { result in
    orders = result
    group.leave()
}

group.notify(queue: .main) {
    // 兩支 API 都回來了
    self.render(profile: profile, orders: orders)
}
```

注意：

- `enter()` 與 `leave()` 的次數必須一致。少呼叫 `leave()`，`notify` 永遠不會觸發；多呼叫則會 crash。錯誤處理的分支也別忘了 `leave()`。
- `group.async(queue:execute:)` 只會追蹤 block 本身，和前面的陷阱一樣，block 裡發出的非同步請求並不會被等待。所以打 API 要用 `enter()` / `leave()`。
- `notify` 是非同步通知，不會卡住目前的 thread。另外還有 `group.wait()` 會阻塞目前的 thread，絕對不要在 main thread 上使用。
- 如果兩個 callback 會在不同 thread 被呼叫，同時修改外面的 `var`，就有 data race 的風險。在 Swift 6 的嚴格模式下，編譯器可能會對這種寫法發出警告或錯誤。

### Swift Concurrency 寫法：async let

數量固定時，用 `async let`：

```swift
async let profile = fetchProfile()
async let orders = fetchOrders()

let (p, o) = try await (profile, orders)
render(profile: p, orders: o)
```

`async let` 宣告的當下就開始執行，兩支 API 會同時進行，到 `await` 時才等待結果。不需要手動配對 `enter` / `leave`，也不需要共享的 `var`。

### Swift Concurrency 寫法：TaskGroup

數量不固定時（例如下載一組圖片），用 `TaskGroup`：

```swift
let images = try await withThrowingTaskGroup(of: UIImage.self) { group in
    for url in urls {
        group.addTask {
            try await downloadImage(from: url)
        }
    }

    var result: [UIImage] = []
    for try await image in group {
        result.append(image)
    }
    return result
}
```

要注意，`for try await` 取得結果的順序是「誰先完成誰先回來」，不是加入的順序。如果需要保持原本順序，可以讓子任務一併回傳 index。

另外，`async let` 與 `TaskGroup` 都屬於「結構化並行（Structured Concurrency）」：其中一個子任務拋出錯誤，或外層任務被取消時，其他子任務也會被通知取消，這是 `DispatchGroup` 沒有的好處。

## 情境 3：數據競爭

多個 thread 同時修改同一個變數，結果會出錯：

```swift
var count = 0
DispatchQueue.concurrentPerform(iterations: 1000) { _ in
    count += 1 // 不是原子操作
}
print(count) // 常常小於 1000，甚至可能 crash
```

### GCD 寫法一：Serial Queue

把所有存取都放進同一個 serial queue，同一時間只會有一個任務在讀寫：

```swift
final class Counter {
    private var value = 0
    private let queue = DispatchQueue(label: "com.example.counter")

    func increment() {
        queue.sync { value += 1 }
    }

    var current: Int {
        queue.sync { value }
    }
}
```

### GCD 寫法二：Concurrent Queue + Barrier（讀寫鎖）

如果讀取遠多於寫入，可以讓讀取同時進行，寫入時再獨佔：

```swift
final class ThreadSafeCache {
    private var storage: [String: Data] = [:]
    private let queue = DispatchQueue(label: "com.example.cache", attributes: .concurrent)

    func value(forKey key: String) -> Data? {
        queue.sync { storage[key] }
    }

    func set(_ value: Data, forKey key: String) {
        queue.async(flags: .barrier) {
            self.storage[key] = value
        }
    }
}
```

帶有 `.barrier` 的任務會等前面的任務全部完成才開始，執行期間 queue 不會跑其他任務。要注意，**barrier 只對自己建立的 concurrent queue 有效**，丟到 `DispatchQueue.global()` 時會被當成一般任務，達不到保護效果。

用 GCD 保護資料還有一個常見的坑：在 serial queue 的任務裡，對**同一個** queue 呼叫 `sync`，會互相等待造成 deadlock。最常見的例子是在 main thread 呼叫 `DispatchQueue.main.sync { }`。

### Swift Concurrency 寫法：actor

`actor` 和 class 很像，但它保證內部的狀態同一時間只會被一個任務存取：

```swift
actor Counter {
    private var value = 0

    func increment() {
        value += 1
    }

    var current: Int {
        value
    }
}

let counter = Counter()

await withTaskGroup(of: Void.self) { group in
    for _ in 0..<1000 {
        group.addTask {
            await counter.increment()
        }
    }
}

print(await counter.current) // 一定是 1000
```

和 GCD 最大的差別是：**這個保護是編譯器強制的**。從 actor 外面存取它的屬性或方法，一定要加 `await`，忘了加會直接編譯失敗，不會像 GCD 一樣「忘了包進 queue 也能編譯通過」。

有一點要留意：actor 的方法執行到 `await` 時會暫停，這段期間其他任務可以進來修改狀態（稱為 reentrancy）。所以在 `await` 之後，不要假設 actor 的狀態和 `await` 之前一樣。

## 回到 Main Thread 更新 UI

UI 只能在 main thread 上更新，兩套方案的寫法如下。

GCD：

```swift
DispatchQueue.main.async {
    self.tableView.reloadData()
}
```

Swift Concurrency：用 `@MainActor` 標記型別或函式，編譯器會確保它們在 main thread 上執行：

```swift
@MainActor
final class OrdersViewModel: ObservableObject {
    @Published var orders: [Order] = []

    func load() async {
        do {
            orders = try await fetchOrders()
        } catch {
            orders = []
        }
    }
}
```

`fetchOrders()` 執行期間不會卡住 main thread，回來之後設定 `orders` 時，又自動回到 main thread 上。

## 從 GCD 遷移：把 Completion Handler 包成 async

舊專案或第三方套件常常只提供 completion handler 版本的 API。可以用 `withCheckedThrowingContinuation` 把它包成 async 函式：

```swift
// 舊的 API
func legacyFetchUser(completion: @escaping (Result<User, Error>) -> Void)

// 包成 async 版本
func fetchUser() async throws -> User {
    try await withCheckedThrowingContinuation { continuation in
        legacyFetchUser { result in
            continuation.resume(with: result)
        }
    }
}
```

`continuation` 必須**剛好 resume 一次**：忘了 resume，呼叫端會永遠等下去；resume 兩次則會 crash。沒有錯誤的情況，可以改用 `withCheckedContinuation`。

這樣就能一步一步把專案改成 async/await，不需要一次全部重寫。

## 總結

| 情境 | GCD | Swift Concurrency |
| --- | --- | --- |
| 依序執行非同步任務 | 巢狀 completion handler | `await` 依序呼叫 |
| 同時執行、全部完成後處理 | `DispatchGroup` | `async let` / `TaskGroup` |
| 保護共享資料 | serial queue / barrier | `actor` |
| 回到 main thread 更新 UI | `DispatchQueue.main.async` | `@MainActor` |
| 取消任務 | 需要自己實作 | 結構化並行自動傳遞取消 |
| Data race 檢查 | 執行時才會發現 | 編譯時期檢查（Swift 6） |

什麼時候還會用到 GCD？

- 維護既有的 GCD 或 Objective-C 程式碼。
- 需要 GCD 獨有的低階功能，例如 `DispatchSource`（計時器、檔案監聽）。
- 與只提供 queue 參數的舊 API 互動，例如某些 delegate 需要指定 callback 的 `DispatchQueue`。

另外要提醒：**不要在 async 函式裡使用 `DispatchSemaphore.wait()` 或 `Thread.sleep` 這類會阻塞 thread 的寫法**。Swift Concurrency 的 thread 數量有限，阻塞它們可能讓整個 App 卡住。需要等待時，改用 `try await Task.sleep(for: .seconds(1))`。

### 附錄：Objective-C 的 GCD 寫法

在 Objective-C 中，用 `dispatch_queue_create` 建立 queue：

```objc
dispatch_queue_t serialQueue =
    dispatch_queue_create("com.example.serial", DISPATCH_QUEUE_SERIAL);
dispatch_queue_t concurrentQueue =
    dispatch_queue_create("com.example.concurrent", DISPATCH_QUEUE_CONCURRENT);

dispatch_async(serialQueue, ^{
    NSLog(@"在 serial queue 執行");
});

dispatch_barrier_async(concurrentQueue, ^{
    NSLog(@"barrier 任務");
});
```

Swift 的 `DispatchQueue(label:attributes:)` 就是這組 C API 的包裝，行為完全相同。
